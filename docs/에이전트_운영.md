# 개발 에이전트 운영 가이드

> `order/에이전트체계_구축_지시서.md` 산출물. `.claude/agents/`의 서브에이전트 5종을 언제·어떻게
> 부르는지 정리한 문서. **이 문서 자체는 사람이 읽는 운영 매뉴얼이지, 에이전트가 참조하는 헌법은
> 아니다**(헌법은 `docs/톤앤매너.md`·`docs/엔진_경계.md`).

---

## 원칙

1. **에이전트는 보고만 한다.** persona-reviewer·tone-keeper·qa-runner·boundary-keeper는 파일을 고칠
   도구 자체를 갖고 있지 않다(Edit·Write 미부여). 발견 사항을 읽고 무엇을 고칠지는 항상 사람이 결정한다.
2. **release-manager만 예외적으로 실행 권한이 있다.** 그래도 병합·태그·push 같은 되돌리기 어려운
   행동 직전에는 반드시 계획을 요약 보고하고 사용자 승인을 확인한 뒤에만 실행 단계로 넘어간다
   (17강 "사람 확인 지점 설계" 원칙 그대로).
3. **보고서는 `order/`에 저장한다.** 파일명 관례: `order/검증리포트_<범위>_<에이전트>.md`
   (예: `order/검증리포트_로비_persona.md`). 지시서와 같은 위치에 두어 "무엇을 시켰고 무엇이
   돌아왔는지"가 한 폴더에 남게 한다.
4. **판단이 애매하면 애매하다고 말한다.** 5종 모두 공통 — 확신 없는 발견을 확정처럼 보고하지 않는다.
5. **같은 저장소를 대상으로 하는 지시서는 동시 실행하지 않는다** — 앞 지시서 완료 보고 후 다음을
   실행한다. 병렬은 저장소가 겹치지 않는 지시서끼리만.
6. **로컬 서버 실행은 `docs/서버_실행_가이드.md`를 그대로 따른다** — 포트가 저장소별로 고정돼
   있어(`netlify.toml` `[dev]`) 옵션 없이 `npx netlify dev`만 실행하면 된다. 임의로 다른
   포트·옵션을 붙이지 않는다(개정: 본진 `order/코드방식_서버설정_지시서.md` B).

## 역할표

| 에이전트 | 역할 한 줄 | 주 호출 시점 | 실행 권한 |
|---|---|---|---|
| `persona-reviewer` | 수강자 페르소나 눈으로 콘텐츠 검증 | 상자(구역) 콘텐츠 완성 직후 | 없음(보고만) |
| `tone-keeper` | 톤앤매너·규격 일관성 감사 | 콘텐츠 완성 직후 / 주기 감사 | 없음(보고만) |
| `qa-runner` | 기능 회귀 검증 일괄 실행 | 모든 구현 작업 후 | 없음(보고만) |
| `boundary-keeper` | 엔진/콘텐츠 경계·백포트 감시 | diff 발생 시 / 병합 전 | 없음(보고만) |
| `release-manager` | 병합·태그·인계 절차 집행 | 마일스톤 마감 시 | **있음**(승인 게이트 필수) |

## 호출 예시

Claude Code에게 그대로 말하면 된다(Agent 도구가 `subagent_type`으로 매칭):

- "로비를 persona-reviewer로 student 관점 검증해줘"
- "미팅룸을 tone-keeper로 감사해줘"
- "qa-runner 돌려줘"
- "이번 커밋 boundary-keeper로 확인해줘"
- "이번 마일스톤 release-manager로 마감해줘" → 계획 보고까지만 나오고 멈춘다. 계획을 확인한 뒤
  "승인, 진행해줘" 같은 명확한 승인을 다시 보내야 실행 단계로 넘어간다.

## 표준 파이프라인

```
콘텐츠 완성
  → persona-reviewer + tone-keeper (병렬 가능)
  → (사람: 발견 사항 보고 검토, 수정 여부·범위 결정)
  → 수정
  → qa-runner (0단계: npm test)
  → boundary-keeper
  → (마일스톤 마감 전) 규범 동기화 검사 — boundary-keeper에게 요청
  → (사람: 승인)
  → release-manager 마감
```

- persona-reviewer·tone-keeper는 "콘텐츠가 맞게 쓰였는가"를 본다 — 서로 다른 렌즈(수강자 체감 vs
  헌법 대조)라 순서 무관하게 병렬로 돌려도 된다.
- qa-runner·boundary-keeper는 "구현이 안 깨졌는가/경계를 넘지 않았는가"를 본다 — 수정이 끝난 뒤,
  병합 전에 돈다.
- release-manager는 앞의 넷이 다 정리된 뒤 마지막에만 부른다.

**시각 검증(qa-runner 필수 단계, `order/시각검증체계_지시서.md` 신설)**: 화면이 새로 생기거나
레이아웃이 바뀐 작업은 qa-runner가 DOM/콘솔 검증만으로 통과 처리하지 않는다 — 375/768/1440px
3개 뷰포트에서 스크린샷을 캡처해 실제로 열어 확인해야 한다(`order/스크린샷_{작업명}/`에 저장).
계기: 연습 책상이 기능 검증(DOM·콘솔)은 전부 통과했는데 화면 배치가 깨진 채(헤더 고립·카드가
좁은 컬럼에 쏠림) 완료 보고된 사고 — DOM이 "정상"으로 읽혀도 배치는 깨질 수 있다는 구조적 공백이
드러났다. 스크린샷 캡처 자체가 실패(Browser 패널 미표시로 인한 타임아웃 등)하면 DOM 검증으로
대체 판정하지 않고, 보고서 최상단에 `⚠ 시각 검증 미수행 — 사용자 육안 확인 필요`를 명시한다
(`.claude/agents/qa-runner.md` 참고).

## 하네스와의 관계 (`order/하네스_구축_지시서.md` 구축 완료)

- **하네스(`npm test`) = 결정론적 검사.** 정답이 정해진 것(강의 수, 필수 필드 존재, 이미지 경로 실존
  등)은 코드로 100% 자동 판정한다 — 판단이 필요 없다.
- **에이전트 = 상황 판단.** "이 사례가 대학생에게 위화감이 없는가", "이 어투가 훈계조인가" 같은 정답이
  하나로 안 떨어지는 판단은 에이전트가 한다.
- `qa-runner`는 회귀 세트의 1단계로 `npm test`를 실행하고 실패 항목을 결과표에 포함한다 — 하네스가
  잡는 것까지 에이전트가 다시 판단하지 않는다(중복 방지).
- **실행법**: 저장소 루트에서 `npm test` (의존성 설치 불필요 — Node 내장 test runner,
  `package.json`에 외부 deps 없음). 내부적으로 `node --test`를 호출한다(디렉터리 경로를 명시
  인자로 주는 형태는 이 환경에서 `MODULE_NOT_FOUND`로 실패해, 인자 없는 기본 자동 탐색 방식을 씀 —
  Node가 `tests/` 하위 `*.test.js`를 기본 패턴으로 자동 인식).
- **구성 3종** (`tests/`):
  - `content-lint.test.js` — `js/data.js` 구조 무결성(강의 수·타입·필수 필드·이미지 경로 실존·
    `closing.teaser`·`slidesVariants` 인덱스 유효성). 사이트별 조정 상수는 파일 상단에 모아둠.
  - `aggregate.test.js` — `netlify/functions/_shared/aggregate.js` 집계 로직(재검사 갱신, 팀 평균,
    필터, 빈 배열 안전성) — 고정 픽스처, 네트워크 없음.
  - `functions-contract.test.js` — `track`/`stats`/`brief` 핸들러 계약(상태 코드, 인증, `global.fetch`
    스텁으로 Supabase/Gemini 차단, "0명 시 AI 미호출" 회귀 고정).
  - `js/data.js` 하단에 Node용 최소 export 심(`typeof module !== "undefined"` 가드) 존재 — 브라우저
    동작에 0 영향(수동 검증 완료).
- **탐지력 검증**: 저장소 밖 임시 사본에 결함 3건(타입 오타·이미지 경로 오타·teaser 삭제)을 심어
  린트가 정확히 3건만 잡아내는지 확인 완료(102개 중 99 pass·3 fail, 오탐·누락 없음).
- 현재 전체 126 테스트 통과. 본진(AX_Lecture)은 86 테스트 — 두 수치가 다른 건 정상이다(이 저장소는
  `slidesVariants` 페르소나 구조 검사 등 고유 블록이 더 있어 본진보다 많음, 공유 엔진 부분
  `aggregate.test.js`·`functions-contract.test.js`는 두 저장소에서 100% 동일).

## 본진판과의 차이

- `persona-reviewer`: 이 저장소는 김주임/박선배/최사장 다중 페르소나를 검증하지만, 본진은 페르소나
  variant 시스템이 아직 이식되지 않아 **실무자 단일 관점**만 본다(대신 07·08강 한정으로 강사 1인칭
  경험판(`slidesPersonal`)이 있다). 본진에 페르소나 variant가 이식되면 이 절을 갱신할 것 —
  `docs/페르소나_작성_가이드.md`의 "본진 이식 메모" 참고.
- `qa-runner`: 이 저장소의 `?variant=<페르소나키>` 표본 항목 대신, 본진 고유의 `?variant=personal`
  (7·8강 경험판)과 진단실(`#/practice`) 항목을 본다.
- 나머지(`tone-keeper`·`boundary-keeper`·`release-manager`)는 두 저장소에서 동일 정의를 쓴다
  (단 `tone-keeper.md`의 §2/§3 관련 세부는 각 사이트 헌법 조문 차이를 반영해 문구가 일부 다름 —
  `docs/엔진_경계.md` §4 "사이트별 조정 허용" 대상).
